# v0.5: Write-side console — acceptance review

v0.5 is complete when the FDE can run the whole loop from the console
with the same guarantees as the CLI: under
[ADR 0004](adr/0004-write-console-triggers.md) the API exposes one run
trigger per loop stage — ingest, project, diagnose, evaluate, execute —
each returning the CLI `--json` payload verbatim plus `api_version`, all
through the same core on the same `canon.db`, and the Web app sequences
them on one Run screen while keeping approval and execution gated
exactly as on the CLI.

## Acceptance checklist

- [x] **Write-side API boundary decided and recorded.** ADR 0004 fixes
  the surface: five named routes mirroring the CLI subcommands, CLI
  `--json` payload parity, domain failures as `200`/`ok: false`
  diagnostics, `STORAGE.WRITE_BUSY` as the only coordination error
  (`503`), armed confirmation for write-back in the UI, and the
  provider/credential rules for diagnosis.
- [x] **All five triggers run through the shared core with CLI
  parity.** `apps/api/tests/test_operational.py::TestRunTriggers` pins
  each route against the CLI's `--json` output on twin workspaces
  (run-specific ids normalized; semantic content, digests, and
  diagnostics identical), the refusal/validation order
  (`DIAGNOSIS.CONFLICTING_ARGS`/`NO_INPUT` before provider resolution,
  `PROJECTION.AS_OF_REQUIRED`, `EVALUATION.REQUIRED_ARGS`), and the
  approval gate (`DECISION.NOT_APPROVED` on an undecided proposal,
  receipt replay on re-execute). `test_write_contention_is_503`
  covers every trigger.
- [x] **Execution stays gated and confirmed.** The core's
  `check_approval` re-evaluates immediately before the adapter call on
  both surfaces; the console adds an armed second click
  (`ExecuteControl`, pinned in `proposals-page.test.tsx`) and renders
  `execution_id`/`attempt`/`receipt`/`replayed` plus refusal
  diagnostics inline.
- [x] **One screen sequences the loop.** `/workspace/run` renders the
  five stages in order, derives the next action from recorded store
  state, posts each trigger, renders results and diagnostics in place,
  and deep-links Trace/Proposals/Reports — pinned by
  `app/test/run-page.test.tsx`.
- [x] **API/Web end-to-end check over both v0.3 workspaces** — the
  whole loop driven through the API triggers on live copies of
  `examples/job-invoicing` and `examples/ticket-sla`, with a CLI twin
  run for parity. Recorded below.
- [x] **Incomplete surfaces are not described as implemented.** The
  limitations below state what v0.5 does not do; the Web fixture mode

## The CLI/Web boundary

Per ADR 0004: the operational surface is **inspection reads, the human
decision write, and one run trigger per loop stage** — every write goes
through the shared core on the shared `canon.db`, so CLI and console are
two transports over one implementation. The CLI remains the reference
surface: every trigger payload is its `--json` output verbatim. Execution
is the only destructive stage; it is doubly gated — `check_approval`
inside the core executor (the authority) and an armed second click in the
UI (accident prevention). Diagnosis defaults to `stub` in the console so
a billed model call is always deliberate.

## Known limitations

- **Synchronous, single-user triggers.** A diagnosis run blocks its
  request for the model call's duration (same as the CLI); ADR 0004
  rejected async submission for v0.5. One user, one store — WAL plus
  bounded `busy_timeout` arbitrates, never a queue.
- **Reviewer/armed identity stays self-asserted** on both surfaces —
  unchanged from ADR 0003, now additionally true for whoever armed the
  write-back. A network-exposed deployment must revisit trust.
- **The API is unauthenticated; the trust boundary is the machine.**
  CORS now allowlists only the console's own origins
  (`ONTOLOGY_API_ORIGINS`, default the Vite dev/preview origins), so a
  page on an unrelated localhost port cannot drive a write trigger
  through a browser — but any local non-browser process can call every
  endpoint, including `execute`, with no credential.
- **No workspace creation, projection authoring, or snapshot-file
  upload** from the console — ingest accepts pasted snapshot text only,
  and `name` is a label, not a path.
- **Deciding over an unindexed legacy proposal still needs the CLI
  first** (v0.4 limitation, unchanged).
- **`trace.jsonl` is best-effort** (v0.4 limitation, unchanged).
- **v0.3/v0.4 limitations carry over**: the delivery adapter is keyed on
  `SendReminder` (G-04), the diagnosis-eval harness embeds a
  job-invoicing fixture (#31), `first_response_at` arrives pre-computed
  (G-06), and no real-data outcome claim is made — `overall: success`
  describes observed cohort differences on synthetic fixtures, never a
  causal claim.

## Release gate

Same discipline as v0.1–v0.4: the repository stays private, no
deployment or publication is performed, and the diagnosis model
selection in [ADR 0002](adr/0002-default-diagnosis-model.md) (status:
pending evidence) still applies — v0.5 verified the write-side boundary
with the deterministic stub provider, not model quality.
