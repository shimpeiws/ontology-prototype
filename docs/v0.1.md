# v0.1: One complete operational loop

v0.1 is complete when an FDE can run the job-invoicing workflow from business understanding through human-approved intervention and outcome evaluation, with inspectable evidence for every stage. Bootstrap `0.0.1` is not v0.1.

See [the product proposal](proposal.md) for the overall scope. The release proves one complete operational loop; it does not require a general ontology platform or production integrations.

## Demonstration workflow

1. Record the business problem: completed jobs are taking too long to reach invoicing.
2. Define the evaluation contract before the model: baseline median 9 days, target median strictly less than 4 days, and invoice-error rate must not increase.
3. Define Job and Person, JobCompleted and InvoiceIssued, the semantic mapping, and the diagnosis task in four workspace configuration files.
4. Ingest baseline and initial CSV/JSON snapshots, then inspect canonical entities, events, and a frozen CompletedButNotInvoiced projection.
5. Run a live AI model against deterministically selected candidates and persist its explanation, cause hypotheses, follow-up questions, and SendReminder proposal.
6. Have the FDE approve or reject the exact proposal. Execute an approved proposal into a local reminders.csv and record the receipt.
7. Import a later source snapshot with invoice timestamps. The adapter must not invent the follow-up business outcome or modify the source to make the demonstration pass.
8. Compare baseline and after cohorts, report pending jobs and guardrails, and inspect the linked trace from observed data through evaluation.

The four FDE definitions are the domain model, mapping, evaluation contract, and agent task. CLI review and configuration files are sufficient; no new frontline UI is required.

## Reference outcome

Synthetic baseline durations 9, 8, 10 yield median 9 days. After durations 3, 3, 4 yield median 3 days. Report improvement of 6 days and strict target attainment. Initial fixtures have no invoice-error evidence: report guardrail unavailable, not passed. Add explicit error-rate evidence to exercise passed and failed guardrails. A 4-day median must remain a target miss.

An honest unavailable/inconclusive report is valid system behavior; it must not be mislabeled as verified business success. The live workflow verifies the machinery, not a claim that synthetic data proves actual business improvement.

## Required negative cases

Malformed mapping/input; missing timestamps; duplicate observations; source correction; ambiguous/negative event intervals; exactly-on-threshold candidates; invalid/disallowed AI proposals; model failure; unapproved/rejected/changed proposal execution; repeated write-back; failed/uncertain execution; pending outcomes; unavailable/failed guardrails.

## Release gate

Keep the repository private through implementation. Review the checklist, deterministic end-to-end test results, repeatable walkthrough, and live-model evidence before declaring v0.1 complete. Select an OSS license and inspect committed fixtures/docs for private data before publication. Visibility change remains a separate maintainer action; no workflow publishes automatically.

When a suitable operational sample becomes available, validate the mapping locally with de-identified real CSV/JSON data. Commit only the procedure and non-sensitive findings. This follow-up checks applicability; unavailable customer data does not block the synthetic v0.1 demonstration.

## Remaining limitations at this checkpoint

- **Default model decision recorded after this checkpoint.** At the checkpoint, [ADR 0002](adr/0002-default-diagnosis-model.md) was `Pending evidence` and the live run passed `--model anthropic/claude-haiku-4.5` explicitly. Issue #51 has since accepted ADR 0002 and set `DEFAULT_MODEL` to that same model.
- **Write-back is a local CSV adapter only.** No real notification is sent; `reminders.csv` under `.ontology/` is the execution receipt, by design for v0.1.
- **The invoice-error guardrail is unexercised in the demonstration data.** Committed fixtures carry no error evidence, so the report correctly says `unavailable`; passed/failed paths are covered only in tests (`test_outcome.py::test_guardrail_unavailable_passed_and_failed`).
- **No de-identified real-data validation yet.** Synthetic snapshots demonstrate the machinery; real-data applicability is the recommended follow-up above.
- **The demonstration asserts an observed cohort difference, not causation.** Post-intervention facts link to interventions as `correlated_intervention`; nothing in v0.1 establishes that the reminder caused faster invoicing.
