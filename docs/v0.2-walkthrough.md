# Walkthrough: the v0.2 FDE authoring flow

This walkthrough takes the job-invoicing workspace through the Web UI — open,
inspect, edit, preview, validate, save — and then reuses the saved YAML in the
v0.1 operational loop unchanged. It complements the CLI-only loop in
[walkthrough.md](walkthrough.md) and implements the end-to-end row of
[authoring-flow.md](authoring-flow.md). The automated equivalent is
`apps/api/tests/test_authoring_loop.py`.

## Setup

From a clean checkout:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e "packages/core[test]" -e "apps/cli[test]" -e "apps/api[test]"

(cd apps/web && npm ci)

# Terminal 1: local API, workspace access restricted to configured roots
ontology-api --root examples            # serves /api/v1 on 127.0.0.1:8000

# Terminal 2: web dev server
cd apps/web && npm run dev              # Vite proxies /api to 127.0.0.1:8000
```

## Authoring steps

1. **Open.** On the home page, open workspace `job-invoicing` (a path inside
   the configured root). The overview shows bundle status and the active
   digest; navigating to an editor never mutates the active bundle.
2. **Domain.** The domain page renders the entity/event/projection graph and
   an equivalent list. Edit a description or add an optional property through
   the structured forms — edits write to the in-memory draft `domain.yaml`,
   marked `unsaved`; the on-disk file is untouched.
3. **Mapping.** Edit bindings or the description on the mapping page, then run
   an isolated preview against a pasted source sample (e.g.
   `id,status,assignee,completed_at,invoiced_at` with a `C01,completed,taro,
   2026-10-17,` row). The preview shows canonical entities/events and
   per-record diagnostics produced by the shared core — using the draft, not
   the saved files.
4. **Evaluation and agent task.** Edit the interval/target text and the agent
   goal through their forms. Property types, comparators, deliverables, and
   condition operators come from `GET /api/v1/contract` — the UI carries no
   hardcoded vocabulary copies.
5. **Validate.** "Validate draft" posts the whole bundle to
   `/drafts/validate`; core diagnostics land on the owning fields. Errors
   block save; warnings do not.
6. **Save.** "Save" posts the draft with the active digest as `base_digest`.
   `saved` re-bases the active bundle; `conflict` (a concurrent on-disk edit)
   keeps the draft and offers an explicit reload; `invalid` returns the save's
   diagnostics; `failed` offers retry. There is no autosave.
7. **Reuse in the operational loop.** `ontology ingest` writes persistent
   runtime state under `.ontology/`; work on a clean workspace — either a
   fresh checkout or remove any prior `.ontology/` first (nothing under it
   is committed). The saved files are exactly what the CLI reads:

   ```bash
   rm -rf examples/job-invoicing/.ontology  # only if a previous run exists
   ontology check examples/job-invoicing
   ontology ingest examples/job-invoicing examples/job-invoicing/data/jobs-baseline.csv
   ontology ingest examples/job-invoicing examples/job-invoicing/data/jobs-current.csv
   ontology project examples/job-invoicing --as-of 2026-10-21T00:00:00Z
   # → candidates Job/C01, Job/C02 — the same result as the CLI-authored files
   ```

   Continuing with `diagnose`/`decide`/`execute`/`evaluate` reproduces the
   v0.1 loop on UI-saved definitions (see [walkthrough.md](walkthrough.md)).

## Negative paths to exercise

- Invalid draft: replace `median` in `evaluation.yaml` draft → save returns
  `invalid` with the core diagnostics; on-disk files unchanged.
- Stale save: edit a YAML file externally between open and save → `conflict`;
  the response carries the live digest for an explicit reload.
- Preview error: a sample row missing `id` produces a rejected-record
  diagnostic in the preview, not a crash.
- Unsaved drafts: an edited definition shows the draft/unsaved indicator
  until saved or reverted; closing the workspace discards browser drafts.

## Boundaries the UI never crosses

The API contract exposes exactly `open`, `validate_draft`, `save`, and
`preview_draft` — there is no proposal, decision, execution, or ingestion
endpoint. Human approval and write-back live only in the operational loop
(CLI), and deterministic mapping/evaluation semantics come from the shared
core in both paths.
