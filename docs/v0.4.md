# v0.4: FDE Operational Console — acceptance review

v0.4 is complete when the FDE can inspect and govern one run in the UI
with the same guarantees as the CLI: the operational surface defined by
[ADR 0003](adr/0003-api-operational-boundary.md) serves trace,
evaluation, and proposal inspection plus human decisions over the same
`.ontology/` store, while ingest, projection, diagnosis, execution, and
evaluation stay CLI-invoked.

## Acceptance checklist

- [x] **API/Web end-to-end check over both v0.3 workspaces** — inspect
  trace and evaluation, approve through the API (the Web decision
  surface), execute via CLI, re-ingest, re-evaluate, inspect again. The
  walkthrough below was run on fresh copies of `examples/job-invoicing`
  and `examples/ticket-sla` against a live `ontology-api` server; every
  API payload was byte-compared with the CLI `--json` output for the
  same query. The automated equivalents are
  `apps/api/tests/test_operational.py::TestCliParity` (job-invoicing)
  and `::TestTicketSlaOperational` (ticket-sla, added for this issue).
- [x] **UI decisions and CLI decisions are indistinguishable to the
  executor and the trace.** `TestDecide` pins both directions: an
  API-recorded approval unlocks `ontology execute`
  (`test_api_approval_honored_by_cli_execute`), an API rejection keeps
  it refused (`test_api_rejection_blocks_cli_execute`,
  `test_reject_then_approve_recovers_through_new_decision`), and a
  later CLI decision supersedes an API one by insertion order
  (`test_cross_surface_latest_recorded_wins`). The recorded decision is
  one append-only row in one `decisions` table — there is no
  surface-specific decision type.
- [x] **Concurrent CLI/API use behaves as ADR 0003 specifies.** WAL
  lets readers see last-committed state while a writer holds the lock;
  a writer past the bounded `busy_timeout` fails whole-transaction as
  `STORAGE.WRITE_BUSY` — `503` over HTTP and a non-zero CLI exit.
  `packages/core/tests/test_storage_coordination.py`,
  `TestDecide::test_write_contention_is_503`, and
  `apps/cli/tests/test_decide_cli.py::test_decide_write_busy_is_stable_code`
  pin the contract; the walkthrough below reproduces it live.
- [x] **Incomplete surfaces are not described as implemented.** The Web
  app offers no execute or run-trigger affordance
  (`proposals-page.test.tsx::renders execution history as status only —
  no execute affordance`,
  `TestDecide::test_no_execute_route`), verdict styling is centralized
  so `unverified`/`unavailable` can never render as success
  (`evaluations-page.test.tsx::an unverified report is never styled as
  success`), and the limitations below state what v0.4 does not do.

Web app consumes exactly these endpoints; its rendering of them is

### 2. Decision-gate negative cases

- A rejection recorded through the API keeps `ontology execute`
  refused (`DECISION.NOT_APPROVED`); a later explicit approval is a new
  append-only decision, and both rows stay inspectable
  (`test_reject_then_approve_recovers_through_new_decision`).
- A decision is bound to the exact `payload_digest`: a changed payload
  fails `check_approval` and cannot execute on any surface
  (`packages/core/tests/test_decisions.py::test_changed_payload_fails_approval`); the
  UI has no execution route at all (INV-003 checklist item).
- Concurrent access per ADR 0003, reproduced live: with a write
  transaction held open on `canon.db`, the API's `proposals/decide`
  waited the bounded timeout and returned
  `503 {"error":{"code":"STORAGE.WRITE_BUSY"}}`, and `ontology decide`
  exited `1` with `ERROR STORAGE.WRITE_BUSY`; after rollback the
  proposal showed only the originally recorded decision — no partial
  write. Readers continued to see committed state throughout.

## The CLI/Web boundary

Per ADR 0003: the API's operational surface is **inspection reads plus
one write — a human approve/reject decision** recorded through the
core's `decide` on the shared `canon.db`. Ingest, project, diagnose,
execute, and evaluate run only from the CLI; the console follows
recorded runs and never starts them, and approval never triggers
delivery — `check_approval` inside the shared execution boundary is the
only gate. In the UI this shows as: Trace and Reports are read-only;
Proposals offers only Approve/Reject behind an explicit reviewer
identity, with executions rendered as status.

## Known limitations

- **No run triggers or execution from the console** (deliberate — ADR
  0003 keeps them CLI-only for v0.4; remote write-back would need
  authentication and delivery confirmation).
- **Reviewer identity is self-asserted** on both surfaces — the same
  trust level as `ontology decide --reviewer` on this single-user local
  tool (ADR 0003 consequence).
- **Deciding over an unindexed legacy proposal needs the CLI first**:
  the read-only surface reports the proposals index as-is and does not
  backfill it; `decide` performs the repair write
  (`test_unindexed_proposals_are_not_backfilled`).
- **`trace.jsonl` is best-effort** — concurrent oversized appends can
  interleave; correctness state lives only in `canon.db`.
- **v0.3 limitations carry over**: the delivery adapter is keyed on
  `SendReminder` (G-04), the diagnosis-eval harness embeds a
  job-invoicing fixture (#31), the UI has no workspace creation or
  projection authoring (G-05), and `first_response_at` arrives
  pre-computed (G-06) — see [v0.3.md](v0.3.md).
- **No real-data outcome claim.** Both demonstrations run on synthetic
  fixtures; `overall: success` describes observed cohort differences,
  never a causal claim about an intervention.

## Release gate

Same discipline as v0.1–v0.3: the repository stays private, no
deployment or publication is performed, and the diagnosis model
selection in [ADR 0002](adr/0002-default-diagnosis-model.md) (status:
pending evidence) still applies — v0.4 verified the operational
boundary with the deterministic stub provider, not model quality.
