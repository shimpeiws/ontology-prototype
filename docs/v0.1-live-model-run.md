# Live-model run evidence for v0.1

One real run of the complete loop against a live provider, run once on
2026-10-07 and recorded here for release review. Nothing below contains
credentials or real customer data: the snapshots are the committed synthetic
files under `examples/job-invoicing/data/`, and the only credential involved
(`OPENROUTER_API_KEY`) stayed in the operator's environment.

## Model selection

- Provider / model: `openrouter` / `anthropic/claude-haiku-4.5`
- Basis: the fixed selection rule in
  [ADR 0002](adr/0002-default-diagnosis-model.md) applied to the measured
  comparison report
  [diagnosis-comparison-2026-10-06.md](diagnosis-comparison-2026-10-06.md)
  (raw measurements in `diagnosis-comparison-2026-10-06.json`). All three
  candidates passed all nine contract checks; the rubric ranking is
  `claude-haiku-4.5` > `gemini-2.5-flash` > `gpt-4o-mini`.
- Status note: ADR 0002 still records `Status: Pending evidence` and
  `DEFAULT_MODEL` remains the provisional `openai/gpt-4o-mini` — Issue #33
  was closed without recording the outcome. This run therefore passed
  `--model anthropic/claude-haiku-4.5` explicitly rather than relying on the
  default. Recording the decision and flipping `DEFAULT_MODEL` remains a
  maintainer action; see the limitations in [v0.1.md](v0.1.md).

## Run

Clean workspace (`no prior .ontology/`), same commands as
[walkthrough.md](walkthrough.md), replacing only the diagnosis provider:

```bash
ontology ingest . data/jobs-baseline.csv   # 3 accepted, 6 events
ontology ingest . data/jobs-current.csv    # 4 accepted, 3 events
ontology project . --as-of 2026-10-21T00:00:00Z   # Job/C01, Job/C02
ontology diagnose . --as-of 2026-10-21T00:00:00Z \
  --provider openrouter --model anthropic/claude-haiku-4.5
```

Diagnosis run `dgx-20261007T043514133641Z-a2932c62` returned `status: ok`,
2 candidates, and contract-valid deliverables — the explanation
(paraphrased): "Two jobs (C01, C02) are completed but not invoiced; both are
assigned to taro, suggesting a process bottleneck or missing trigger." Three
labeled hypotheses with fact/observation citations and four follow-up
questions. Two validated `SendReminder` proposals were persisted:

- `…-a2932c62-p0` — Job/C01 → taro ("completed 4 days ago, not yet invoiced")
- `…-a2932c62-p1` — Job/C02 → taro

- guardrail invoice-error-rate **unavailable**; overall **unverified**

## What this proves and does not prove

The live run proves the machinery works with a real model: real output is
contract-valid, grounded in supplied evidence, persistable through the
human-decision gate, and traceable through re-observation to the evaluation
report. It does not prove a real business improvement — the cohorts are
synthetic, and the `unverified` overall status is the honest label the system
reports when a guardrail lacks evidence.
