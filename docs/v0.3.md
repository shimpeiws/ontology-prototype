# v0.3: Generality across workflows — acceptance review

v0.3 is complete when two unrelated workflows run through the same core
with definitions alone — no workflow-specific identifiers, semantics
registries, or code branches in `packages/core`. The second workflow is
the support-ticket first-response SLA recorded in
[ticket-sla-walkthrough.md](ticket-sla-walkthrough.md); the gaps it
exposed and their resolution are logged in
[generality-gaps.md](generality-gaps.md) (G-01–G-03 resolved by #55,
#56, #57; G-04–G-06 accepted below).

## Acceptance checklist

- [x] Both workspaces pass check → ingest → project → diagnose → decide
  → execute → evaluate → trace in CI. `apps/cli/tests/test_loop_cli.py::test_complete_loop_stub_provider`
  drives job-invoicing and `apps/cli/tests/test_ticket_sla_cli.py::test_ticket_sla_complete_loop`
  drives ticket-sla through every stage with the deterministic stub
  provider, including the approval gate, the reminder write-back with an
  idempotent replay, and a fully linked trace export. CI also runs
  `ontology check` against both `examples/` workspaces on every push and
  pull request.
- [x] job-invoicing still produces the v0.1 reference outcome — median 9
  → 3, strict `lt 4` target attained, invoice-error guardrail evaluated
  from fixture evidence (`test_complete_loop_stub_provider`; unchanged
  by the v0.3 work).
- [x] UI-authored definitions for the second workflow load in the CLI
  with identical diagnostics. `apps/api/tests/test_authoring_loop.py::test_ticket_sla_ui_saved_bundle_loads_in_cli`
  opens the ticket-sla workspace through the API, applies structured-form
  edits to all four definitions, saves through the digest-checked atomic
  save path, and asserts `ontology check` reports the same diagnostics as
  the committed workspace.
- [x] No workflow-specific identifiers (entity/event/metric names)
  appear in `packages/core/src`. `packages/core/tests/test_boundaries.py::test_core_has_no_workflow_identifiers`
  derives the banned identifier set from the declared definitions of
  every `examples/` workspace — domain, entity, event, projection,
  metric, guardrail, and action names — scans the core Python sources,
  and permits only the documented exceptions below. Adding a third
  example workspace extends the check automatically.

## Known limitations

- **The delivery adapter is keyed on the action name (G-04).**
  `CsvReminderAdapter` delivers `SendReminder` proposals only; both
  workflows declare that action, and the identifier check allowlists it
  in `execution.py`. A workflow needing a distinct intervention would
  need a new adapter — accepted for v0.3.
- **The diagnosis-eval harness embeds a job-invoicing fixture (issue
  #31).** `packages/core/src/ontology_core/eval_fixtures/` is a frozen
  workspace and canned outputs the deterministic harness replays; it is
  test data the check exempts, not semantics the loop depends on.
- **No workspace creation or projection authoring in the UI (G-05).**
  The ticket-sla definitions were authored as YAML text and round-trip
  through the UI's structured editors and save path; creating a
  workspace or a new projection in the UI remains unassigned scope
  ([authoring-flow.md](authoring-flow.md#gaps-and-unassigned-requirements)).
- **`first_response_at` arrives pre-computed (G-06).** The ticket export
  carries the field directly; deriving a first-response event from a raw
  replies export needs earliest-per-subject event selection the
  condition language does not express.
- **No real-data outcome claim.** The de-identified applicability check
  from #58 found no suitable sample; the procedure is committed in
  [real-data-validation.md](real-data-validation.md) and does not block
  v0.3. Both demonstrations run on synthetic fixtures and claim no real
  business improvement.

## Release gate

Same discipline as v0.1/v0.2: the repository stays private, no
deployment or publication is performed by this workflow, and the
diagnosis model selection in
[ADR 0002](adr/0002-default-diagnosis-model.md) (status: pending
evidence) still applies — v0.3 verified generality of the pipeline with
a deterministic provider, not model quality.
